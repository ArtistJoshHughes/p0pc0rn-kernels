# Design notes

The kernels are WGSL generated by JavaScript: each op builds its shader text for a configuration (tile sizes, prologue, epilogue, precision), compiles it once per configuration through the pipeline cache, and splits the work into dispatches sized from the device's measured speed.

## Runtime (`src/core/gpu.js`, `src/core/tune.js`)

- **`createGpu(opts)`** requests an adapter and a device with `shader-f16` (required) and `subgroups` (used where present). It raises every limit the kernels use to the adapter's maximum.
- **Buffers** are counted (`alive`, `peak`) and pooled: a freed buffer is kept for reuse by the next request of exactly the same size and usage, and cleared before it is handed out again. `freeAll()` and `drainPool()` release everything.
- **`Runner`** batches dispatches into command buffers. A batch's uniform parameters live in one uniform buffer (256-byte slots, written just before submit). A batch is submitted when its estimated GPU time reaches 80 ms or it holds 512 dispatches.
- **Dispatch sizing.** Each op splits its grid so that one dispatch takes at most `maxDispatchSeconds` (0.2 s by default), using `gpu.rate` from `calibrate()`. Long dispatches are dangerous: on the iPhone, a 0.6 s attention dispatch reset the GPU. On Windows, D3D12 can merge a whole submit, and a 2 s watchdog then resets the GPU.
- **`calibrate(gpu)`** measures the GEMM (both accumulation modes) and attention, and sets `gpu.rate`.
- **`defaultTune(gpu)`** sets the kernel choices: fp16 partial sums in the GEMM and the phone-tuned attention.
  - The `TUNE_TABLE` entry for this GPU family goes on top: entries come from shared **Tune for this device** results and match on the adapter's vendor and architecture.
  - Ops read `gpu.tune`, and arguments can override it per call.
  - GEMM tiles can be tuned per weight encoding (`q4`, `q8`, `f16`) or per convolution kind (`conv`, `conv3`). The convolution setting wins for convolutions.

## GEMM family (`src/ops/gemm.js`)

`gemm(gpu, args)` computes `Y[m, n] = Σₖ X'[m, k] · W[n, k]` (y = x·Wᵀ), with weights in one of the encodings in [FORMAT.md](FORMAT.md).

- **Tiles.** 64×128 output tiles by default (`DEFAULT_TILE`), 128 threads, an 8×8 register tile per thread, and k-steps of 32 through workgroup memory.
- **Dequantisation in the kernel.** 4- and 8-bit codes become an fp16 tile in workgroup memory; the full-precision weight never exists in device memory.
- **Accumulation.** Either fp32, or fp16 partial sums over each 32-k step added into fp32 accumulators (`acc: 'f16'`, the default from `defaultTune`). Pure fp16 accumulation was faster but too inaccurate (see [RESULTS.md](RESULTS.md)).
- **Prologues** (how X is read): `f16` (plain); `lnmod` (LayerNorm plus adaLN modulation, fused); `rms` (RMSNorm, fused); `conv` (implicit-GEMM 2D convolution over HWC: 3×3 or 1×1, stride 1 or 2, fused nearest-2× upsampling, optional fused GroupNorm-apply plus SiLU); `conv3` (3×3×3 convolution over THWC, below).
- **Epilogues** (how Y is written): `f16` or `f32` store; `resadd` (fp32 residual += gate · acc); `swiglu` and GeGLU (gate and up rows interleaved); `heads` (QK-RMSNorm, RoPE, head-major Q/K/V write for attention); `bias` (+ bias, optional in-place residual); `onormgate`.
- **One rule for Apple GPUs:** never store a single component of a `vec4` in workgroup memory. On Metal that becomes a read-modify-write of the whole vector and races, so tiles are transposed in registers and written as whole vectors.

### 3×3×3 convolution (`conv: {kind: 'conv3', ...}`)

An implicit GEMM over a THWC fp16 clip, stride 1. Time padding repeats the edge frames (`stride` carries the clip's frame count T); space pads with zeros. An optional fused PixelNorm plus SiLU applies before the zero padding (`pn`). Each thread works out its rows' voxel indices once and each 32-k step's tap once, instead of per element. That hoisting is bit-identical and 9–15% faster on the iPhone.

**Time chunks.** Three fields let a caller run the convolution over part of a clip, so a video decoder can work on a few frames at a time with much less memory:

| Field | Meaning |
|---|---|
| `padT` | the first output frame of this call (the call's rows start there) |
| `padL` | the input buffer starts at clip frame `padL` |
| `ks` | if > 1, the input is a ring of `ks` frames: clip frame t sits at slot t mod `ks` |

With `padT = padL = 0, ks = 1` the call covers the whole clip. The tests check that two-frame chunks, and a three-frame ring, give output bit-identical to one whole-clip call.

## Attention (`src/ops/attention.js`, `src/ops/video.js`)

All attention kernels are flash attention: the L×L score matrix never leaves the workgroup. Scores, softmax statistics and accumulators are fp32. Q is `[Hq][Lq][D]` and K/V are `[Hkv][Lk][D]` (head-major, as the GEMM's `heads` epilogue writes them); O is written token-major at column `h·D` (the input layout of the output projection).

Masks:
- `mode 0`: none.
- `mode 1`: causal plus valid length. Key j is visible to query i if j ≤ min(i, nvalid − 1).
- `mode 2`: valid length only. Key j is visible if j < nvalid.

GQA: query head h reads kv head ⌊h / (Hq/Hkv)⌋.

- **`attention()`** (head 128) is the standard kernel. It uses 32- or 64-query tiles, with an optional subgroup reduction, and drops to a 16-query variant on devices with 16 KB of workgroup memory.
- **`attn256()`** (head 256, with an optional Gemma-style soft cap) is the standard 16-query kernel, plus a split variant for small workgroup memory. Its dispatches are sized at a third of the attention rate, since it runs about three times slower than the head-128 kernel.
- **`attnF()`** is the register-tiled, phone-tuned kernel for heads of 128 (`ATTNF_P`, 64 queries × 64 keys) and 256 (`ATTNF_V`, 32 queries × 128 keys).
  - Q stays resident in workgroup memory; partial sums for QK (per 32-dimension chunk) and PV are fp16, flushed into fp32, with an exact online softmax.
  - It needs 32 KB of workgroup memory (`attnFFits`); `attention()` and `attn256()` route to it when `gpu.tune.attnF` or `gpu.tune.attnF256` is set and it fits.
  - It is 1.6–1.9× (head 128) and 3.8–3.9× (head 256) faster than the standard kernels on the iPhone.

## Small kernels (`src/ops/misc.js`, `src/ops/video.js`, `src/ops/video2.js`)

- **Normalisation:** row statistics for LayerNorm and RMSNorm; GroupNorm statistics in an exact two-pass over the whole tensor, so a decoder working in bands has no seams.
- **Elementwise and layout:** elementwise ops (residual add, casts, SiLU, GELU, SwiGLU, adaLN modulate, Euler step); row softmax; fp16 transpose; direct convolution for tiny channel counts (3 → 128, 128 → 3).
- **Video-model kernels:**
  - gated linear-attention preparation and KV-state reduction (SANA-Video);
  - per-head RMSNorm with RoPE, and the Gemma post-norm residual;
  - pixel statistics and depth-to-space for the LTX-2.3 decoder, both with per-chunk output offsets for time-chunked decoding.

## What the phone taught

- **Interleave every comparison.** Heat moves a phone's speed by 40–50% within minutes, so run A and B alternately on the same inputs, and rest between long runs. A canary (a fixed GEMM) before and after shows how hot the device got.
- **Kernel gains shrink in a full render.** The phone is limited by power and heat, so a render gains about half of what a kernel gains on its own.
- **Safari on iPhone has no `subgroups`.** Reductions go through workgroup memory.
- **What looked faster on paper often lost:** padding, prefetching, wider tiles and mixed-precision pipe splitting all lost (see [RESULTS.md](RESULTS.md)). Measure on the device.
